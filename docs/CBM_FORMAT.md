# CBM — Clonify Building Model (`.cbm`) — Format Specification v1

The `.cbm` file is Clonify's custom 3D building format. It is generated by
the cloud compiler (`server/src/services/cbm.js`) when a client finishes
building setup, and it is the **single source of truth** consumed by:

- the **robot** (`robot/.../clonify_core/cbm.py`) — nav graph, walkable
  grids, elevator profiles, charging targets;
- the **dashboard** (`web/src/components/cbmThree.js`) — renders the
  combined floors as a 3D building for the Overview / POV-3D / POV-Cam
  views.

A `.cbm` is a UTF-8 JSON document with a fixed schema, a magic tag and a
SHA-256 checksum. JSON was chosen over a binary layout so models diff well
in support tooling; the RLE walkable encoding keeps files compact.

The walkable grid behind each floor is produced automatically from the
uploaded blueprint by the OpenCV floor-plan analyzer
(`server/floorplan/analyze.py`, invoked via
`server/src/services/autoDetect.js`) — a classical, weights-free computer-
vision pipeline built on the same open-source stack (OpenCV / SciPy /
scikit-image) the published floor-plan recognition research uses
(CubiCasa5K, DeepFloorplan, Raster-to-Vector). It binarises the image,
isolates walls by stroke thickness + directional morphology (dropping text,
dimension marks and furniture), finds the building interior by flooding the
exterior, and downsamples to the cell grid. For a clean blueprint the upload
is enough; the analyzer only returns a few targeted `uncertain` regions
(each a cell list + a yes/no question) where a human decision genuinely
resolves ambiguity — an isolated pocket, or a sealed/furniture-filled room.
The client answers those on the map, and can still paint/erase by hand. A
deep-learning segmentation model can be dropped in behind the same JSON
contract later (see `analyze_dl()`); if Python/OpenCV is unavailable the
service degrades to a basic in-process threshold.

## Top level

| field | type | meaning |
|---|---|---|
| `magic` | `"CBM1"` | format identifier / version gate |
| `version` | int | monotonically increasing per recompile; robots resync when it changes |
| `generated` | ISO-8601 | compile timestamp |
| `building` | object | `id`, `name`, `address`, `siteElevationM`, `exteriorPhoto` |
| `floors` | Floor[] | ordered by `level`, ground = 0 |
| `graph` | Graph | combined multi-floor navigation graph |
| `pois` | Poi[] | named points (delivery points, lobby, charging) |
| `elevators` | Elevator[] | building-specific elevator profiles |
| `charging` | Charge[] | charging pad locations (`nodeId`, `floor`, `x`, `y`) |
| `checksum` | hex | SHA-256 of the document without this field |

## Floor

```jsonc
{
  "level": 0,
  "name": "Ground floor",
  "elevation": 0.0,        // metres above building origin (cumulative floor heights)
  "height": 3.0,           // storey height, metres
  "grid": {
    "cols": 40, "rows": 30,
    "cellSize": 0.5,       // metres per cell
    "walkableRle": [120,0, 6,1, ...]   // run-length pairs [count, value]
  },
  "blueprint": "ab12…png", // uploaded blueprint image (served from /uploads)
  "photo": "cd34…jpg"      // real-life photo of the floor
}
```

The walkable grid is painted by the client over the blueprint in the floor
editor. Cell `(x, y)` maps to world metres `((x+0.5)·cellSize, (y+0.5)·cellSize)`
with the floor's `elevation` as the vertical offset — this is how the
renderer extrudes all floors into one 3D building.

## Graph

- `nodes`: `{ id, floor, x, y, type }` — one node per walkable cell
  (`type:"cell"`, id `f<level>:<x>,<y>`), plus POI nodes (`poi:<level>:<id>`)
  and elevator nodes (`elev:<elevatorId>:<level>`). Coordinates in metres.
- `edges`: `{ a, b, w, kind }` — 4-connected walk edges weighted by
  `cellSize`; `kind:"elevator"` edges join the same shaft across floors with
  a fixed ride-time weight (15) so Dijkstra prefers same-floor paths.

Both the cloud dispatcher (JS) and the robot (Python) run the identical
Dijkstra over this graph, so routes agree on both sides.

## Elevator profile (building-specific)

```jsonc
{
  "id": 3,
  "label": "Elevator A",
  "doorType": "single_door",         // or "double_door"
  "cells": { "0": {"x":12,"y":7}, "3": {"x":12,"y":7} },  // cabin cell per served floor
  "panel": {
    "callKeyIndex": 0,                // actuator pin for the call button
    "keys": [                         // key layout mapped during calibration
      { "index": 3, "label": "1", "floor": 1, "row": 0, "col": 1 }
    ]
  },
  "panelHeightMm": 1200,              // mast height to reach the in-car panel
  "callButtonHeightMm": 1050,         // mast height for the hall call button
  "calibrated": true                  // set after manual on-site calibration
}
```

Navigation, obstacle avoidance and the lock system are generic across all
units; elevator profiles carry everything building-specific for the
multi-floor feature.

## Blueprint-only, no questions

The pipeline is **blueprint-only**: floor blueprints alone build the 3D
model (vectorization + extrusion, per the research above) — real-life photos
and the exterior/elevation images are optional context, not requirements.
Room segmentation takes all interior free space as navigable, so the
analyzer resolves the plan automatically and never asks the operator
questions. An optional elevation (side-view) blueprint can be uploaded to
convey storey heights.

## Compile-time validation

The compiler refuses to emit a `.cbm` unless: every floor has a blueprint
**and** an analyzed walkable grid; a charging POI exists; and multi-floor
buildings have at least one elevator placed on ≥ 2 floors. Real-life and
exterior photos are optional.
